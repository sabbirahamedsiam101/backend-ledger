# Transaction Lifecycle & Ledger Design

In a banking or financial ledger system, moving money between accounts must be atomic, immutable, and safe from duplicate executions. Below is the structured flow and data schema for handling a transaction.

## 1. The Transaction Flow (Step-by-Step)

When a user initiates a money transfer from **Account A** to **Account B**, the system processes it through the following phases:

* **Request Reception:** The system receives the transfer request along with a unique token to prevent double-spending.
* **Ledger Entry Creation:** Before any money moves, the system creates a pending ledger transaction record. This acts as the single source of truth.
* **ACID Execution:** 
  * Debit Account A (subtract the amount).
  * Credit Account B (add the amount).
* **Status Update:** The transaction status is updated based on whether the debit/credit operation succeeded or failed.

---

## 2. Core Transaction Data Schema

Every transaction record must contain specific metadata to ensure auditability and security:

* **From Account:** The unique identifier (ID) of the sender's account.
* **To Account:** The unique identifier (ID) of the receiver's account.
* **Amount:** The financial value being transferred (typically stored as an integer in the smallest currency unit, e.g., cents, to avoid floating-point errors).
* **Idempotency Key:** A unique string (usually a UUID) generated by the client. It ensures that if a network timeout occurs and the request is retried, the system executes the transaction exactly once.
* **Status:** The current state of the transaction lifecycle (e.g., `PENDING`, `COMPLETED`, `FAILED`).
